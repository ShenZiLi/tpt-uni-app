# 太平通 2.0 微信小程序原型技术选型与设计文档

## 1. 文档目的

本文档用于指导“太平通 2.0”微信小程序原型的开发与汇报演示，目标是快速完成一套可在微信开发者工具中运行、可点击操作、可展示核心产品理念的高保真原型。

本版本不追求正式上线，不建设真实业务后台，不接入真实保单、理赔、支付或 AI 服务。

## 2. 项目背景

根据现有设计调研，太平通 2.0 计划从“功能堆叠型保险服务台”升级为“AI 风险管理伙伴”，重点体现：

- AI 顾问：用自然语言帮助用户查询和理解保障信息；
- 保单管理：集中展示个人及家庭保单；
- 闪赔服务：突出理赔入口和进度体验；
- 家庭保障：以家庭成员为中心组织保障关系；
- 健康陪伴：通过健康任务和活动增加持续使用；
- 可配置体验：支持默认版、银发版和主题换肤的产品设想。

## 3. 本次原型目标

### 3.1 汇报目标

让汇报对象能够在 3～5 分钟内理解：

1. 太平通 2.0 的产品定位变化；
2. AI 如何串联保险、家庭和健康场景；
3. 用户如何完成一次从发现问题到获得服务的操作；
4. 视觉和交互上与现有版本的差异。

### 3.2 原型目标

- 可在微信开发者工具中启动和预览；
- 页面跳转、Tab 切换、弹窗、表单和状态变化可用；
- 使用本地 Mock 数据模拟业务结果；
- 不依赖网络接口，汇报时不受后端或账号状态影响；
- 代码结构具备后续接入真实接口的空间。

### 3.3 明确不做

- 真实登录、实名认证和手机号授权；
- 真实保单查询、核保、投保和支付；
- 真实理赔材料上传与审核；
- 真实大模型调用和敏感数据处理；
- 完整运营后台、埋点系统和权限体系；
- 多端正式发布适配。

## 4. 技术选型结论

### 4.1 推荐技术栈

```text
uni-app
  └── Vue 3
        └── TypeScript
              └── Vite
                    ├── uni-ui
                    ├── 本地 Mock 数据
                    ├── uni-app 路由与 Storage
                    └── 微信开发者工具预览
```

### 4.2 选型理由

| 方案 | 结论 | 说明 |
| --- | --- | --- |
| uni-app | 采用 | Vue 单文件组件开发，后续可扩展 H5 或其他端 |
| Vue 3 | 采用 | 组件化和组合式 API 适合快速搭建多个原型页面 |
| TypeScript | 采用 | 为 Mock 数据、页面状态和后续接口预留类型约束 |
| Vite | 采用 | Vue3 uni-app 项目的默认高效构建方案 |
| uni-ui | 采用 | 基础表单、列表、弹窗、导航组件覆盖度较高 |
| 本地 Mock | 采用 | 保证演示稳定，避免后端依赖 |
| Pinia | 暂不采用 | 当前页面数量和状态复杂度不足以引入全局状态管理 |
| uniCloud | 暂不采用 | 原型阶段无需云端数据和用户体系 |
| Taro | 不采用 | 多端能力不是本次核心目标，增加选型和编译复杂度 |
| 原生小程序 | 备选 | 如果未来确认只维护微信端，可再迁移或新建原生版本 |

uni-app 官方支持 Vue3、TypeScript 及微信小程序编译输出；Vue3 版本基于 Vite，并会将页面编译为微信小程序所需的 WXML、WXSS 和 JS 文件。[uni-app 官方文档](https://uniapp.dcloud.net.cn/tutorial/)

### 4.3 组件库建议

第一阶段使用 uni-ui 完成通用控件；品牌视觉和核心卡片使用自定义组件实现，避免页面被组件库默认样式限制。

建议自定义以下组件：

- `TpSectionHeader`：模块标题和查看更多入口；
- `PolicyCard`：保单摘要卡片；
- `FamilyMemberCard`：家庭成员保障卡片；
- `AiMessageBubble`：AI 对话消息气泡；
- `ActionShortcut`：首页快捷服务入口；
- `HealthTaskCard`：健康任务和进度卡片；
- `EmptyState`：无保单、无理赔记录等空状态。

## 6. 汇报演示主流程

### 流程 A：AI 查询保单

```text
首页
  → 点击 AI 顾问
  → 点击“我有哪些医疗保障？”
  → 展示 AI 思考态 / 回复
  → 展示医疗保单摘要
  → 点击“查看保障详情”
  → 进入保单详情
```

### 流程 B：闪赔服务

```text
首页
  → 点击“我要理赔”
  → 选择理赔类型
  → 展示材料清单
  → 点击“开始申请”
  → 展示提交成功和进度时间线
```

### 流程 C：家庭保障

```text
首页
  → 点击家庭保障卡片
  → 查看家庭成员
  → 选择成员
  → 查看该成员的保障缺口
  → 点击“让 AI 帮我分析”
  → 展示建议结果
```

### 流程 D：健康行动

```text
首页
  → 点击健康行动
  → 查看任务列表
  → 点击“完成今日步行”
  → 展示任务完成反馈
  → 更新健康积分
```

## 7. 页面设计要求

### 7.1 首页

核心任务：让用户知道“现在最值得做什么”。

页面模块建议：

1. 顶部用户问候和风险状态；
2. 主视觉 AI 顾问卡片；
3. 待办事项，如保单即将续期、理赔待补材料；
4. 我的保障摘要；
5. 快捷服务；
6. 家庭保障和健康行动。

首页不采用大量同权重功能宫格，优先使用场景卡片、待办卡片和主动建议。

### 7.2 AI 顾问页

AI 页只做“可控的演示对话”，不接真实模型。

- 提供 4～6 个推荐问题；
- 点击问题后按预设脚本返回答案；
- 支持输入框和发送按钮；
- 回复中展示可点击的业务卡片；
- 用加载动画模拟思考过程；
- 对敏感或未知问题返回“当前为演示数据”的提示。

### 7.3 保单页

- 顶部展示保障总览；
- 支持全部、人身、健康、财产分类；
- 卡片展示产品名称、被保人、保额、状态；
- 详情页展示保障责任、缴费信息、服务入口；
- 通过本地状态模拟“已收藏”和“已查看”。

### 7.4 服务页内容

服务入口可先作为首页模块或独立页面，不强制加入底部 Tab。

- 闪赔：类型选择、材料清单、提交成功；
- 产品对比：两款产品的保障范围、保额、保费和免赔额对比；
- 保单健诊：展示风险提示和建议；
- 健康行动：任务、积分和完成反馈。

### 7.5 我的页

- 个人信息卡片；
- 家庭成员入口；
- 设置入口；
- 主题换肤入口；
- 银发版入口，演示字号、颜色和按钮尺寸变化。

### 8.3 本地状态

仅保留演示必需状态：

- 当前 Tab；
- 当前用户模式：普通版 / 银发版；

状态优先放在页面或 composable 中，跨页面需要共享时使用 `uni.setStorageSync`。不在第一版引入复杂的全局状态管理。

## 10. 视觉与交互规范

### 10.1 视觉方向

本项目采用“浅薰衣草 + 玻璃感白卡 + 深靛蓝”的主视觉方向，参考素材来自 `/Users/shen/Studio/Work/太平通2.0/2.0原型UI/UI风格参考`。参考图中的角色、品牌名称和文案不直接复用，统一转译为太平通自己的“吉象” IP。

#### 设计关键词

> 浅薰衣草背景、半透明白卡、深靛蓝文字、蓝紫渐变、高留白、圆角胶囊、轻量拟人化 AI。

#### 色彩和材质

| 角色 | 建议方向 | 使用场景 |
| --- | --- | --- |
| 页面背景 | 浅薰衣草 / 低饱和蓝紫 | 页面底色和大面积留白 |
| 主文字 | 深靛蓝 | 标题、核心数据、主要操作 |
| 主强调色 | 蓝紫渐变 | 吉象 AI、主按钮、选中状态 |
| 健康状态 | 翡翠绿 | 完成、健康、正向趋势 |
| 风险提醒 | 柔和橙色 | 待处理、风险提示、活动状态 |
| 卡片表面 | 半透明白色 | 内容容器和功能卡片 |

#### 布局和组件

- 内容使用大圆角白色卡片承载，卡片之间保持充足留白；
- 卡片使用轻微透明、柔和阴影和细边框，形成轻玻璃质感；
- 服务入口采用两列或多列圆角卡片，避免密集的功能宫格；
- 首页优先采用“状态卡片 + 建议卡片 + 行动按钮”的结构；
- 数据优先使用圆环进度、数字指标、趋势标签和时间线；
- 底部导航使用悬浮胶囊式设计，当前 Tab 使用深靛蓝高亮；
- 页面标题字号偏大，辅助文字使用灰蓝色，保证信息层级清晰；
- AI 顾问使用吉象头像、插画或轻量动态状态形成独立识别。

#### 吉象 IP 规则

- 吉象是太平通自有的保险与健康服务伙伴，不使用参考图中的“阿福”角色形象；
- 吉象承担“解释、提醒、引导和陪伴”角色，不表现为医疗诊断者或理赔决策者；
- 吉象视觉可以使用头像、插画、表情和状态动画，但应保持统一的深靛蓝与蓝紫渐变识别；
- 对话内容采用短句、大白话和明确下一步动作，避免客服话术堆叠。

### 10.2 交互原则

- 一个页面只突出一个主操作；
- 重要业务结果必须有明确反馈；
- 所有演示按钮都必须能完成闭环；
- 不展示“暂无功能”的死入口；
- 网络、登录、授权等不确定因素全部使用本地模拟；
- 动效以状态反馈为主，不影响汇报操作速度；建议使用淡入、滑入、进度变化和 AI 思考态，不使用复杂 3D 动效。

### 10.3 银发版演示

通过根节点 class 切换样式：

```text
page-root
├── theme-default
└── theme-senior
```

银发版重点变化：字号增大、对比度提高、按钮变大、减少装饰信息、减少页面层级。无需在原型阶段复制一套页面。

## 11. 开发与预览方式

### 11.1 开发方式

推荐使用 HBuilderX 或 uni-app CLI 创建项目，使用 Vue3 + TypeScript 模板。

### 11.2 微信预览

```bash
npm install
npm run dev:mp-weixin
```

然后在微信开发者工具中导入编译生成的微信小程序目录，检查：

- 页面路由是否正常；
- TabBar 是否正常；
- 图片和字体资源是否正常；
- 弹窗和表单是否正常；
- 真机安全区域和滚动效果是否正常。

uni-app 会将 Vue 页面编译为微信小程序页面；微信开发者工具作为最终预览和调试环境。[uni-app 编译器说明](https://uniapp.dcloud.net.cn/tutorial/compiler)

## 12. 风险与规避

| 风险 | 处理方式 |
| --- | --- |
| uni-ui 样式与品牌视觉不完全一致 | 基础控件使用 uni-ui，核心卡片自定义 |
| 跨端语法限制 | 第一版只验证微信小程序，不使用 DOM、window 等浏览器 API |
| AI 接口不稳定 | 使用预设问答脚本和本地延迟模拟 |
| 汇报时网络或账号异常 | 不依赖登录和远程接口 |
| 页面数量膨胀 | 只完成四条主流程，其余入口做收敛 |
| 过早建设后台 | 预留 service 层接口，暂不接后端 |
| 复杂动效影响性能 | 只使用淡入、滑入、加载态等轻量动效 |

## 13. 验收标准

### 技术验收

- 项目能成功编译到微信小程序；
- 微信开发者工具无阻断性报错；
- 页面、TabBar 和返回操作正常；
- 本地 Mock 数据能够稳定展示；
- 关键按钮不存在空操作；
- 普通版和银发版样式可切换。

### 汇报验收

- 3～5 分钟可完成至少两条完整流程；
- 首页能体现“主动服务”而非单纯功能列表；
- AI 顾问有明确的输入、回答和业务结果；
- 保单、理赔、家庭和健康至少各有一个可展示触点；
- 演示过程无需登录、无需等待接口、无需人工修复数据。

## 14. 实施顺序

1. 创建 uni-app Vue3 + TypeScript 项目；
2. 配置页面、TabBar、主题变量和基础组件；
3. 完成首页和保单列表；
4. 完成 AI 顾问预设问答流程；
5. 完成闪赔和家庭保障流程；
6. 完成健康行动和我的页面；
7. 增加银发版和主题切换；
8. 使用微信开发者工具进行页面和真机检查；
9. 按汇报脚本清理无效入口和异常状态。

## 15. 最终决策

本项目原型阶段采用：

> **uni-app + Vue 3 + TypeScript + Vite + uni-ui + 本地 Mock 数据 + 微信开发者工具**

该方案满足当前的快速开发、可操作演示和后续扩展要求。原型阶段不引入后端、云数据库、Pinia、真实 AI 服务和复杂权限体系；待产品方向确认后，再根据正式上线要求补充服务端、鉴权、接口层、埋点和数据安全方案。

## 16. 市场亮点设计借鉴

市场亮点调研已独立整理至：[保险类产品亮点功能调研.md](./保险类产品亮点功能调研.md)。本设计文档采用其中的筛选结论，不直接照搬竞品功能。

### 16.1 本次原型纳入

- 吉象 AI 顾问：以预设问题和 Mock 回复演示保单查询、解释和服务导航；
- 家庭保障中心：按家庭成员查看保单、保障状态和缺口；
- 保单随存随懂：将保障责任、除外责任和下一步动作结构化展示；
- 保单健诊：用保障雷达和缺口清单展示分析结果；
- 闪赔协助：演示事故类型、材料清单、提交成功和进度时间线；
- 产品对比与理赔案例：作为产品详情或服务入口展示；
- 银发模式：通过字号、对比度、按钮尺寸和页面层级切换体验；
- 健康行动：以步行任务、打卡和积分反馈演示健康陪伴。

### 16.2 本次仅保留为长期方向

商保直付网络、自动调解、健康数据定价、AI 闪应用、复杂多模态输出和大型健康营销活动暂不作为当前原型已具备能力。它们需要真实业务系统、合作网络、合规规则或运营资源支撑，后续应单独论证。

### 16.3 原型表达边界

所有 AI、理赔和健康相关结果均使用 Mock 数据，仅用于展示交互和产品理念，不代表真实核保、理赔、医疗或保险推荐结论。
